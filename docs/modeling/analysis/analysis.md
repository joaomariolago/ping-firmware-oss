# **Object-Oriented Analysis - Ping Firmware Open Source (OSS)**

---

## **1. General Description of the Problem Domain**

### **1.1 Overview**

The **Ping Firmware Open Source (OSS)** is a modular, software-defined framework for acoustic sensing and communication. Its main objective is to provide a flexible and extensible platform for sonar devices, offering core functionality for common operational modes while enabling straightforward extension and customization.
The software stack is platform-agnostic and can be ported to various Microcontroller Units (MCUs) and Microprocessor Units (MPUs) with differing architectures and capabilities.

It supports multiple operational modes:

* **Echosounder** - for range measurement using monotone, chirp, or encoded pulses;
* **Acoustic Modem** - for underwater acoustic communication, supporting multiple modulation schemes;
* **Doppler Velocity Logger (DVL)** - for estimating underwater vehicle velocity through Doppler shift analysis;
* **Multibeam Sonar** - for range measurement using multiple transducers, enabling beamforming and image reconstruction;
* **Custom** - for user-defined waveforms used in testing and research.

The software is structured into five primary layers (**From closest to hardware to highest level**):

* **Hardware Abstraction Layer (HAL)** - handles direct interaction with hardware components;
* **Modulation/Demodulation Layer (MDL)** - manages the modulation and demodulation of acoustic signals;
* **Digital Signal Processing Layer (DSPL)** - performs digital signal processing operations;
* **Control Layer (CTL)** - governs system control and coordination;
* **Application Layer (APL)** - provides high-level application logic and user interaction.

Each layer is responsible for a specific set of functionalities and remains independent of the others. Layers communicate through well-defined interfaces. When hardware support is unavailable, software-based or simulated (SITL - Software In The Loop) implementations can be used as substitutes.

#### **1.1.2 Design Principles**

The architecture of the Ping Firmware Open Source is guided by the following principles:

* **Modularity** - each layer encapsulates a well-defined set of responsibilities and interacts with other layers exclusively through explicit interfaces. This enables independent development, testing, and replacement of components.
* **Portability** - the design minimizes hardware- and platform-specific assumptions, allowing the firmware to be ported across different MCUs and MPUs with minimal changes, primarily confined to the HAL.
* **Determinism** - timing, data paths, and control flows are designed to be predictable, with particular emphasis on deterministic sampling, processing, and actuation suitable for real-time acoustic applications.

### **1.2 Hardware Abstraction Layer (HAL)**

#### **1.2.1 Purpose**

The **Hardware Abstraction Layer (HAL)** forms the foundation of the system. It isolates the rest of the firmware from hardware-specific details such as MCU peripherals, drivers, board layout, and the analog front end.
Its role is to provide clean, high-level primitives (e.g., "transmit this waveform with gain X" or "capture N samples from channel Y with gain Z") without requiring higher layers to know:

* which timer, DMA channel, or ADC instance is used;
* how the transducer is biased;
* whether transmission is generated by a DAC, a PWM timer, or an external codec;
* whether reception originates from an IF I/Q interface or directly from the transducer element.

In essence, HAL defines what is physically possible for a given sonar board and exposes those capabilities in a standardized form.

At a high level, HAL is divided into two operational blocks:

1. **HAL::TX** - transmit-path control
2. **HAL::RX** - receive-path control

Additionally, HAL includes shared and utility services (timing, buffering, calibration, safety interlocks, etc.).

#### **1.2.2 Responsibilities**

The HAL layer must provide:

1. **Initialization and Configuration**
   * Initialize clocks, GPIOs, DAC/PWM generators, analog output stages, programmable-gain amplifiers (PGA/OPAMP), ADCs, DMA engines, timers, and bias networks.
   * Report capabilities (e.g., "supports chirp," "has beamforming delay lines," "supports external I/Q feed").

2. **Deterministic Timing**
   * Apply programmable transmit and receive delays for beamforming and time alignment across multiple elements.
   * Guarantee deterministic sampling intervals for RX data.

3. **Waveform I/O Primitives**
   * TX: Set waveform mode (MONOTONE, CHIRP, PSK, FSK, or custom) and load waveform samples from upper layers.
   * RX: Configure input path mode (RAW or IF).

4. **Front-End Conditioning**
   * TX output gain and drive level.
   * RX input gain and bias (DC offset tuning and centering).
   * Selection between internal ADC, external ADC, or analog feed-through paths.
   * Configuration of analog filters and demodulators (e.g., IF mixer or I/Q demodulator path).

5. **Data Movement**
   * Single or double-buffered DMA capture.
   * Continuous or synchronous data acquisition modes.

6. **Protection and Safety**
   * Enforce safe limits for output drive, duty cycle, repetition rate, and bias voltage.

### **1.3 Modulation/Demodulation Layer (MDL)**

#### **1.3.1 Purpose**

The **Modulation/Demodulation Layer (MDL)** bridges the digital signal domain and the physical layer managed by HAL.
Its primary responsibility is to **encode outgoing data into an acoustic waveform** suitable for transmission and to **decode incoming sampled data** into a digital representation usable by upper layers.

This layer may be bypassed if the hardware supports direct modulation and demodulation, allowing upper layers to configure the hardware directly.
The MDL does **not** perform higher-level DSP tasks such as energy detection, echo profiling, or Doppler estimation - these are handled by the **DSPL**. Instead, it provides the **baseband modulation and demodulation mechanisms**.

#### **1.3.2 Responsibilities**

1. **Waveform Generation (Modulation)**
   Generates the time-domain signal according to the selected modulation scheme and parameters received from the Control Layer:

   * **MONOTONE** – single-frequency continuous wave for echosounder pings.
   * **CHIRP** – linear or nonlinear frequency sweep.
   * **PSK** – phase-shift keying for data transmission.
   * **FSK** – frequency-shift keying for robust communication in noisy channels.
   * **CUSTOM** – arbitrary user-defined waveform provided through the protocol interface.

   The output is a digital waveform buffer compatible with HAL::TX. Optional preprocessing (scaling, windowing, phase alignment) may be applied before transmission.

2. **Signal Demodulation**
   Converts raw or I/Q data from HAL::RX into a **symbol stream or baseband signal**:

   * For **monotone** and **chirp**, provides filtered or down-mixed baseband data.
   * For **PSK/FSK**, performs correlation, carrier recovery, and phase/frequency detection.
   * For **custom** modes, applies a configurable demodulation pipeline.

   The result is an intermediate stream suitable for higher-level DSPL processing.

3. **Synchronization and Framing**
   Manages symbol alignment, start-of-frame detection, and basic timing recovery to maintain coherence between TX and RX.

4. **Light DSP Preprocessing**
   Performs limited digital operations required for modulation or demodulation if not handled by hardware:

   * Sinusoid synthesis, phase accumulation, and numerically controlled oscillators (NCO).
   * Simple FIR/IIR filtering for band-limiting or baseband extraction.
   * Quadrature generation.

---

### **1.4 Digital Signal Processing Layer (DSPL)**

#### **1.4.1 Purpose**

The **Digital Signal Processing Layer (DSPL)** extracts **high-level information** from the digitized signals provided by lower layers.
It transforms raw or baseband samples into measurable quantities such as echo strength, range, energy, and signal quality metrics.
Unlike the **MDL**, DSPL does **not** handle waveform generation or modulation schemes - its role is strictly **analytical**.

This separation ensures modulation logic remains encapsulated within MDL while DSPL provides a **unified, reusable analysis framework** across sonar modes.

#### **1.4.2 Responsibilities**

1. **Signal Conditioning**
   Applies generic, non-modulation-specific operations to prepare signals for analysis:

   * DC offset removal and amplitude normalization.
   * Windowing and smoothing.
   * Basic filtering (band-limiting or noise reduction).
   * Equalization.

2. **Feature Extraction**
   Computes measurable features and metrics:

   * **Peak detection** for echo localization.
   * **Energy estimation** and **envelope profiling**.
   * **Threshold detection** for event triggering.
   * **Noise-floor estimation** and **SNR computation**.

3. **Temporal and Spectral Analysis**
   Provides analytical tools for signal characterization:

   * Time-domain statistics (RMS, variance, zero-crossing rate).
   * Frequency-domain analysis using FFT or correlation.
   * Envelope and phase tracking for Doppler or motion inference.

4. **Profile Aggregation and Post-Processing**
   Aggregates results over multiple pings or frames to improve stability:

   * Averaging, filtering, and accumulation.
   * Adaptive thresholding based on recent history.
   * Statistical outlier rejection.

5. **Processing Pipelines**
   Defines configurable analysis chains (e.g., *filter -> detect -> measure -> report*) that can be customized by the Control Layer according to mode or mission.

---

### **1.5 Control Layer (CTL)**

#### **1.5.1 Purpose**

The **Control Layer (CTL)** manages **autonomous operation, adaptive control, and high-level coordination** of sonar channels or transducers.
It acts as the **decision-making layer** between DSPL analysis and system-level logic in the APL, maintaining operational states, applying feedback, and ensuring consistent performance under varying conditions.

Each transducer or sensing unit operates under its own CTL instance. For example, a DVL with four transducers instantiates four CTLs, each managing its corresponding TX/RX path.
The APL aggregates these CTLs to define overall system behavior.

#### **1.5.2 Responsibilities**

1. **Operational State Management**
   * Maintains runtime state for each sonar channel.
   * Handles range tracking, ping sequencing, and mode transitions.

2. **Adaptive Parameter Control**
   * Adjusts TX gain, pulse length, and repetition rate based on range or echo strength.
   * Tunes RX gain and thresholds using DSPL feedback (e.g., SNR or noise floor).
   * Adapts range windows to maintain bottom lock or follow moving targets.

3. **Feedback Integration**
   * Uses DSPL metrics to refine operational decisions.
   * Applies smoothing, hysteresis, or predictive filtering for stability.

4. **Coordination and Synchronization**
   * Aligns timing across multiple channels.
   * Manages shared control signals for synchronized transmissions.
   * Prioritizes channels under resource constraints.

5. **Interface with the Application Layer (APL)**
   * Reports high-level measurements and status (e.g., range, velocity, signal quality).
   * Communicates health, confidence, or tracking state.
   * Accepts configuration commands from APL (e.g., depth mode, power limits).

---

### **1.6 Application Layer (APL)**

#### **1.6.1 Purpose**

The **Application Layer (APL)** is the highest layer of the firmware hierarchy and serves as the **interface between the sonar system and external control systems or users**.
It implements the main operational logic for each sonar mode and coordinates CTL instances to produce application-level data products.

APL handles **mode-specific logic**, **data fusion**, and **communication management**, converting raw and intermediate data into high-level information accessible via external interfaces.

#### **1.6.2 Responsibilities**

1. **System Coordination and Mode Management**
   * Initializes and manages CTL instances.
   * Controls transitions between sonar modes (Echosounder, DVL, Multibeam, Acoustic Modem).
   * Ensures consistent timing and configuration across all channels.

2. **Data Fusion and High-Level Processing**
   * Aggregates and interprets CTL data.
   * For **DVL**, combines per-transducer data into unified inertial estimates.
   * For **Multibeam**, merges beam data into composite profiles or images.
   * For **Echosounder**, reports range and echo strength.
   * For **Acoustic Modem**, interfaces with the communication protocol for data transfer.

3. **Communication and Interface Handling**
   * Implements the external command and telemetry protocol (serial, Ethernet, etc.).
   * Provides structured access to configuration, status, and measurement data.
   * Handles command parsing, data packaging, and result reporting.
   * Manages error handling, acknowledgments, and feedback.

> For this project, only the **Echosounder** mode (monotone operation) is specified.
> The **DVL**, **Multibeam**, and **Acoustic Modem** modes will be defined in future revisions.
> Requirements are derived from the existing Ping Protocol by Blue Robotics.
